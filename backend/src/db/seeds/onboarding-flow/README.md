# Onboarding-flow seed chain

Five scripts, run in order, that build a complete pipeline from a brand new
tenant all the way to a populated onboarding record — so the Onboarding
workboard has something real to show without touching any existing data.

Not part of the main reset flow (`seed.js` / `run-script.js`) — these are ad
hoc, standalone scripts.

## Run order

```
cd backend
node src/db/seeds/onboarding-flow/01-tenant.js
node src/db/seeds/onboarding-flow/02-job.js
node src/db/seeds/onboarding-flow/03-sourcing-applicant.js
node src/db/seeds/onboarding-flow/04-candidate.js
node src/db/seeds/onboarding-flow/05-onboarding.js
```

| Step | Creates |
|---|---|
| `01-tenant.js` | Company, role (with full CRUD permissions), user, linked together |
| `02-job.js` | One `core_job` under that company, plus a 5-stage custom pipeline (Screening & Matching → Interview → Assessment → Background Check → Offering & Contract) |
| `03-sourcing-applicant.js` | An `internal`-platform `core_job_sourcing` linked to the job, one `master_applicant`, and sample screening Q&A (what "Kecocokan preferensi" reads from) |
| `04-candidate.js` | Promotes the applicant to a real pipeline candidate (`master_candidate`), parked at the final stage, with a passing AI Match score |
| `05-onboarding.js` | An accepted `candidate_offer`, then calls the real `OnboardingService.createOnboarding()` — checklist, Day-1 schedule, milestones, and D30/D60/D90 check-ins are generated by the actual service templates, not hand-rolled here |

## Configuration

Edit `config.js` once — every script reads from it and resolves everything
else **by name** (company name, job title, applicant name), not by numeric
id, so there's nothing to copy-paste between steps.

## Re-running

Every step (except the onboarding record insert itself, in step 5) is
idempotent — looked up before insert, so re-running the whole chain with
the same `config.js` just reports "already exists" instead of duplicating.
Step 5 skips calling `createOnboarding()` again if an onboarding record
already exists for that (candidate, offer) pair, since the service always
generates a fresh checklist/schedule/milestone set rather than upserting.

## Why this exists

The previous `../seed-onboarding.js` only inserted the bare
`candidate_onboarding` row — no checklist, schedule, milestones, or
check-ins — and required an already-accepted offer to exist by hardcoded
id, with no path to get there from scratch. It also bundled in unrelated
onboarding-chatbot document indexing. This chain covers the whole
lifecycle instead, and reuses the real `OnboardingService` for the
onboarding sub-records so they're guaranteed to match what a real accepted
offer produces.

## Heads-up: stale schema files

While building this, found that `backend/src/db/onboarding-schema.sql` and
`backend/src/db/migrations/010_onboarding_module.sql` both still reference
a `master_companies` table that doesn't exist (should be `core_company`) —
running either against a fresh database would fail outright. Not fixed as
part of this task since `setup.sql` (what `run-script.js` actually applies)
already has the correct, consolidated version — but those two files are
stale/dead and worth deleting or fixing if anyone goes looking at them later.
